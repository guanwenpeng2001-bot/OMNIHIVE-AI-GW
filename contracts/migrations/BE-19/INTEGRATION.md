# Payment, entitlement and wallet evidence

## Rollout

Apply 308 after 300 and 305. Size a maintenance window for the payment order table rewrite, index creation and immutable historical snapshots. Drain order, entitlement and wallet mutations during the migration. The existing migration transaction installs the compatibility triggers and takes the cutoff snapshots together. Keep Ent automatic schema creation disabled on migrated databases. Its legacy schema declarations still specify two decimal places for order amounts.

BE-11 remains the only producer of wallet openings and double-entry postings. An exact command updates the locked USD payer row via `payment_write_balance`; the same database trigger records commands from older binaries. Never add a second wallet posting in a handler. Existing openings and posting IDs survive the migration. `payment_wallet_evidence` resolves the command, receipt and reversal/adjustment references. Historical imported command IDs identify the imported entry. They cannot identify the original caller.

New orders freeze the source amount, actual provider minor units, currency, fee rate, fee-ceiling-v1 and plan terms. JPY uses whole units, USD/CNY two decimals and KWD three. ISK/UGX keep whole values submitted as multiples of 100. Three-letter currency parsing follows the payment adapter. Historic orders preserve the stored source amount. An unknown historical currency, a rounded third digit, or an unproven historical fee rule remains null. Recover missing facts from the provider statement before moving such an order to exact callbacks. Do not invent a wallet movement when importing old entitlements.

## Composition

1. Construct `payments.Store{DB: db, Fulfillment: paymentService, Refresh: refresh}`. The existing payment service satisfies the fulfillment interface. Supply a post-commit callback that invalidates the payer's billing and auth caches, and the subscription cache for a nonzero group ID. It runs again on redelivery of a reversal.
2. At the existing v1 webhook's verified-notification dispatch, call `store.HandleVerified(ctx, resolvedProviderKey, notification)` for a migrated order. Use the validating instance's result directly. Keep the existing signature verification, response bodies and callback URLs. Filter historical cohorts using persisted order terms before choosing the dispatcher. Keep v1 query-based confirmations and historical `sub2_N` resolution on their existing verified path until their inputs carry exact identity. The migration guards order capture and records fulfillment from both versions. Never run both dispatchers for one notification. A wrong instance cannot select the order. Return the existing unknown-order acknowledgement only for a positively verified foreign/unknown order, and retry database failures and pending reversal evidence.
3. Configure Stripe notifications for payment intent success/failure, refund.created, refund.updated and charge.dispute.closed. A succeeded refund or a closed lost dispute identifies its effect by refund/dispute ID. A reversal arriving before fulfillment gets a retryable response. Distinct deliveries of the same effect share one deduction. The handler serializes transitions on the order and bounds cumulative reversals by the exact captured amount. Wallet allocation uses the cumulative rounded proportion, which conserves the source amount. The wallet deduction is capped at available balance. The reversal records the theoretical source allocation and links the actual posting, which can be smaller or absent. Subscription reversal shortens the originally granted subscription by its cumulative share of whole days. Preserve these historical references even if the subscription has expired.
4. Stripe requests initiated through the existing admin refund workflow carry signed return metadata identifying the order. Route their confirmations through the store. The original workflow owns the deduction or the operator's explicit choice to waive it. A missing legacy refund identity or a conflicting local refund amount requires reconciliation against the statement. Existing refund/query adapters continue to handle the other payment rails.
5. Redeem, transfer, promotion and admin adapters can call `RedeemBalance`, `TransferAffiliate`, `ApplyPromotion`, `SetWallet` and `AdjustWallet`. Pass the same UUID for transport and commit retries. For user/admin entry points keep caller authorization, redeem rate limiting, inviter accrual, email, admin audit and post-commit cache invalidation in the owning service. FundingResult returns the original exact before/after/delta for compatibility response DTOs, including retried and no-op commands. These methods own the funding transition. They must replace the corresponding mutation in that service. A second distinct redemption still consumes the source once. A retry of a transfer cannot take awards credited after the first transfer. The v1 transfer compatibility trigger restores the exact locked quota and audit snapshots when its float scan lost a fractional unit.
6. Register `internal/control/payments.Register(v2, Handler{Store: store, Access: identityStore, Step: totp}, sessionMiddleware...)` and compose BE-19 with BE-01/16. A session-bound step-up and billing.adjust are required to PUT a same-payer evidence link. Linking another payer also requires billing.payers.read and workspace membership. GET requires project billing.read. Only the payer sees personal command and wallet IDs. BE-16's scoped, settled receipt supplies the charge or entitlement consumption. Missing observations remain null. Keep the existing BE-16 legacy quota window reader for older subscriptions.
7. For a capture committed before worker loss, use the existing v1 payment retry operation or redeliver the original verified event. Capturing payment and executing fulfillment have separate commit boundaries. A failure after capture leaves the durable PAID order, and v1's fulfillment lease, redeem claim and subscription assignment transaction recover it.

## Writer census

| Current writer | Wallet/entitlement path and cutover |
| --- | --- |
| User creation, bootstrap, default signup credit | The initial users.balance numeric value creates one immutable BE-11 opening. Read its exact value from the wallet event. |
| OAuth first binding and legacy user/usage services | auth_oauth_first_bind adds the provider default. user_service and usage_service call UpdateBalance/DeductBalance. These use the same BE-11 trigger. Keep the v1 settings/input DTOs until their owners provide the command identity. |
| Admin set/add/subtract and wallet correction | user_repo SetBalance/AdjustBalance and admin_user use a separate legacy admin audit record. Replace the monetary call with SetWallet/AdjustWallet and retain the audit/caches. BE-16 adjustments already supply their own command ID and original/adjustment posting through billing_adjustment_effects. |
| Recharge and direct redemption | payment_fulfillment reuses RedeemService, and redeem_service uses UpdateBalance/ApplyRedeemBalanceAdjustment. The source transition and wallet posting share a transaction. Switch positive or negative balance redemption to RedeemBalance inside the authorized flow. Concurrency, invitation and subscription redemption keep their type-specific semantics. |
| Registration promotion | promo_service uses promo_code_usages and UpdateBalance. ApplyPromotion owns the atomic counter, usage and exact wallet credit for a converted caller. |
| Inviter accrual, thaw and transfer | affiliate_repo maintains frozen/available quota, the transfer claim and affiliate ledger. TransferAffiliate performs the thaw and transfer without a float scan. The database records accrue/transfer identities and freezes old transfer snapshots. Accrual stays a separate entitlement until transferred. |
| Subscription assignment, renewal and plan purchase | subscription_service/user_subscription_repo own the effective term and counters. Payment assignment uses the existing unique SUBSCRIPTION_ASSIGNED audit in the grant transaction. The migration captures actual entitlement transitions, plan, payer and order. Usage-window counters remain on their legacy accounting path. |
| Payment refund, rollback and chargeback | Legacy admin payment_refund uses DeductAvailableBalance, UpdateBalance and subscription extension/revocation. Its multi-transaction rollback is still required for already-pending refunds. Migrated external reversals use the order lock and the single wallet writer. |
| Gateway receipt, quota and batch-image funds | usage_billing_repo/usage_settlement_receipt_repo own captured charges and batch-image reserve/capture/release. api_key_budget_repo owns reserve, release and expiry. Their existing mixed-worker holds, legacy fingerprints and float command inputs remain under BE-11. |
| BE-19 payment commands | No duplicate balance column or independent posting writer. Cash funding goes through payment_write_balance and the BE-11 trigger. payment_commands, payment_provider_events and payment_reversals provide durable identities. |

Current v1 Ent return types, provider display amounts, legacy receipt and quota command inputs, and pre-cutover pending refunds still include floats. Contract each caller only after the replacement reaches its entry point and in-flight commands have drained. Provider display amounts cannot serve as stored minor-unit evidence. Movement attribution uses same-payer, single-source/single-movement transactions or an explicit command. Unknown or ambiguous historical associations remain absent.
